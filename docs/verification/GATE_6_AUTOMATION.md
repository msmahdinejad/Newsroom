# Gate 6 — Collection & Reporting Automation Verification

## Collection runs separately from reporting

Collection is a continuous bounded loop (`newsroom-collector`), independent
of the six-hour reporting schedule (`newsroom-scheduler`). Reports are
generated by the scheduler/pipeline from already-collected material.

## Safe configurable intervals by platform (config)

| Setting | Default (s) | Scope |
|---|---|---|
| `COLLECT_INTERVAL_TELEGRAM_SECONDS` | 300 | Telegram/X frequent incremental |
| `COLLECT_INTERVAL_X_SECONDS` | 1800 | X (Agent-Reach-backed) |
| `COLLECT_INTERVAL_RSS_SECONDS` | 900 | RSS/Atom conditional |
| `COLLECT_INTERVAL_WEB_SECONDS` | 3600 | websites conservative bounded |
| `COLLECT_INTERVAL_GITHUB_SECONDS` | 1800 | repo + release polling |
| `COLLECT_INTERVAL_YOUTUBE_SECONDS` | 1200 | channel incremental |
| `COLLECT_INTERVAL_REDDIT_SECONDS` | 900 | bounded incremental |
| `COLLECT_LOOP_SECONDS` | 900 | collector loop cadence |

## Requirements verified

- **PostgreSQL-backed cursors** — `collection_cursors` table; cursor advances
  only after persist success (`pipeline/cursors.py`). 37 cursors persisted.
- **No concurrent polling of the same source** — pipeline advisory lock
  (`pipeline/lock.py`); `max_instances=1` + `coalesce=True` on scheduler.
- **Bounded concurrency** — `COLLECT_CONCURRENCY=4`.
- **Bounded backfill** — `COLLECT_LIMIT_PER_SOURCE=10` per pass.
- **Retry delay with jitter** — `COLLECT_RETRY_BASE_DELAY_SECONDS` /
  `COLLECT_RETRY_MAX_DELAY_SECONDS`; recoverable errors retry, rate-limit
  (429) and 403 classified recoverable.
- **Rate-limit awareness** — Reddit 429/403, httpx timeouts all recoverable.
- **Restart continuation** — cursors survive restart (verified, see
  GATE_6_RESTART); no full-history re-scan (soak cycle 2 yielded 0 new items
  from the same source → cursor idempotency).
- **Item-level idempotency** — `content_hash` dedup at the raw layer;
  re-collecting the same source creates no duplicate raw items.
- **No repeated full-history scans** — overlap band + seen-id sets.
- **No excessive repeated provider/subprocess calls** — Agent-Reach
  subprocesses only when enabled + pinned; native collectors use httpx
  directly with bounded connection pools.

## Scheduled reports (Asia/Tehran, independent of host/container tz)

Four jobs registered in PostgreSQL (`apscheduler_jobs`):

| Job ID | Cron (Tehran) |
|---|---|
| `report_00` | 00:00 |
| `report_06` | 06:00 |
| `report_12` | 12:00 |
| `report_18` | 18:00 |

- `coalesce=True`, `max_instances=1`, `misfire_grace_time=300` → duplicate
  and missed-tick handling. Verified by integration test
  `test_gate6_scheduler` (4 jobs, hours 0/6/12/18, minute 0).

Each scheduled run: selects material since the last delivered scheduled
report, excludes delivered unchanged stories, deduplicates/clusters
cross-platform, ranks, runs the hierarchical editorial pipeline, renders a
Persian report, delivers every Telegram chunk, persists message IDs, and
advances the boundary **only after complete delivery**. PostgreSQL
coordination prevents duplicate runs (advisory lock + `max_instances=1`).

## Catch-up after downtime

APScheduler `coalesce=True` collapses missed ticks into one run; at most one
catch-up run is produced (misfire grace 300s; older misfires are dropped, not
flooded).

## No-news path (verified live)

When no important new material exists since the boundary: zero editorial
provider calls (`editorial_attempts` count unchanged), one short Persian
no-news notice persisted (`generation_method=none`, `story_ids=[]` so no
stories marked delivered), delivered via Telegram with a persisted message
ID, and the scheduled cursor advances. See GATE_6_LIVE_REPORT.
